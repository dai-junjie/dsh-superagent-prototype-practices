# 案例一：一个问题在飞书与 GitHub 之间持续推进

> 场景化使用案例，不是已完成的项目复盘。以下对话为虚构示例，说明工作如何衔接；没有实测耗时或收益结论。

## 团队遇到什么问题

测试同学在群里报了一个可复现的问题，开发者希望 agent 先修复并提交 PR。真正麻烦的往往不是第一次写代码，而是后续评审：意见在 GitHub，最初的需求在飞书，执行上下文又在某个编码会话里。人需要记住在哪里继续，并把上下文搬过去。

## 实际怎么用

以一个已有“无结果提示”设计约定的搜索页面为例：

1. **测试在飞书报问题。** 在已配置的群里 @ Superagent：“搜索无匹配内容时页面空白，预期显示项目已有的‘暂无结果’提示。复现步骤是……请修复、补验证并提 PR，不要合并。”给出允许公开的测试数据与复现线索，不贴真实用户信息。
2. **Superagent 接住任务。** 核对仓库约定和复现条件，在独立任务中修改、验证，形成可审阅 PR。缺少必要信息时在原处提出具体问题，而不是擅自决定新设计。
3. **开发者直接在 PR 审阅。** 例如指出：“普通无匹配状态对了，但清空筛选后不应继续显示空状态，请补这个分支。”开发者不必再把这段意见复制到另一个编码会话。
4. **Superagent 在原任务中继续修改。** 评审意见作为后续输入关联到任务，执行者判断范围并处理，验证后更新同一个 PR。超出原任务的新需求则另行处理，不因为出现在评审中就无限扩张。
5. **回到最初的飞书话题交付。** 测试同学从原话题获得 PR 入口和可审阅结果；开发者仍在 GitHub 决定是否合并。可审阅不等于已合并，发出消息也不等于问题已经上线。

这条链路的重点是同一任务跨入口持续推进，而不是让人在每一步重新指挥。UI 类修复还需要按团队约定提供真实的修改前后对照，不能只交一段“已经修好”的文字。

## Superagent 负责什么，人负责什么

- Superagent：接收团队入口的请求，把任务、执行上下文与 PR 关联，处理范围内的后续反馈，将可用结果送回来源。
- 测试同学：提供复现条件并确认是否符合业务现象。
- 开发者：审阅代码和验证证据，决定设计、风险取舍与合并。

这种衔接依赖已配置的消息来源、仓库访问、任务订阅及健康的服务；不是任意群消息或任意仓库评论都会被处理。

## 与继续使用 Codex 的分工

如果一个开发者正在本地集中排查、探索多种实现，直接在 Codex 中保持高频交互往往更顺手，不必先把任务送进群聊流程。这里沿用团队“Codex 是主力编码工具”的用法，不断言其他产品缺少集成能力。

Superagent 补的是团队协作层：需求与评审本就在不同入口，人可以留在原处推进。编码执行仍是其中一环，两者不是“只能选一个”的替代关系。

**值得观察的收益：** 后续评审是否真的无需人工搬运；人员切换后是否仍能找到同一任务；结果是否回到原话题。若大家仍须转述每条意见、追问任务在哪，协作层的价值就还没有体现。本文不把这些收益写成已验证事实。
