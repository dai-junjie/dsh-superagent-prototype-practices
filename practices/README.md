# 实践案例

分为**基础练习**与**生产实践**：前者帮助动手理解机制，后者说明团队在什么场景下值得使用 Superagent，以及与主力编码工具 Codex 如何配合。两者都不冒充已完成的实测。

## 生产实践

以下是面向真实团队工作方式的场景化案例，人物、问题与对话均为示例，**不是已上线案例或实测复盘**。重点是“怎么用、谁接手、产出什么、何时不适合”，不是实验作业。

| 使用场景 | 实际怎么用 | 相比团队当前用 Codex 的方式，值得验证的收益 |
| --- | --- | --- |
| [一个任务跨飞书和 GitHub 持续推进](01-message-to-pr.md) | 飞书报问题 → 修复并提 PR → 开发者在 PR 提意见 → 继续修改 → 回原话题交付 | 少搬运评审意见，不必记住原来在哪个编码会话 |
| [多人共用 Agent，独立任务并行推进](02-team-parallel.md) | 甲排错、乙补测试、丙改文档；一个任务等人时，其他任务可继续 | 在原入口提需求，减少个人维护和专人追踪会话的负担 |
| [从团队反馈中主动跟进明确问题](03-proactive-follow-up.md) | 接收群反馈，按事先授权规则评估并处理明确问题，有用结果再交付 | 减少发现消息、整理需求、再次派单的工作；前提是少误判、少打扰 |

## Codex 与 Superagent：互补而非替代

这里的 Codex 指团队当前作为主力的交互式编码工作方式，不是对其全部产品能力的穷举或竞品测评。

| 工作需要 | 更合适的使用方式 |
| --- | --- |
| 开发者集中排查、探索实现、连续作判断、快速迭代 | 继续以 Codex 为主，人在编码上下文中直接推进 |
| 团队成员从飞书/GitHub 异步发起明确请求，跨入口评审和交付 | 用 Superagent 维护任务与反馈链路，编码执行是其中一环 |
| 在群反馈中发现尚未正式派单的明确问题 | 有限接收、事先授权和主动规则下使用 Superagent；不默认监听所有讨论 |

Superagent 补的是团队入口、任务持续跟进和协作组织，不是“更强的代码生成器”。也不意味着 Codex 不能接入外部系统或并行工作。选择依据是团队的协作负担，而非工具标签；并发、权限和人工审阅仍需维护者管理。
