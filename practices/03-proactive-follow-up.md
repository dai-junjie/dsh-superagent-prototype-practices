# 案例三：从团队反馈中主动跟进明确问题

> 场景化使用案例，不是实测复盘。以下反馈和规则为示例，并未因此修改当前部署的接单策略。

## 团队遇到什么问题

有人在群里顺手反馈：“CSV 导出只要筛选到零条记录就会报错，测试样例和复现步骤在这里……”这是一条有价值的线索，但没有人正式派单。如果必须由开发者先发现消息、整理成需求，再打开编码工具，反馈可能被遗漏。

Superagent 可以补这一段：在事先授权的范围内关注团队反馈，尝试把明确问题推进为可用结果。它不是默认监听所有群，也不是看到抱怨就开始改代码。

## 实际怎么用

**先由维护者确定范围。** 例如只接入一个项目反馈群和对应仓库，约定：“对与本仓库有关、提供复现步骤且能按既有行为判断正确结果的小缺陷，可以尝试定位和局部修复；主观体验建议、产品取舍和跨模块重设计不自动实施；交付可审阅结果，由人合并。”

要接住未 @ 的反馈，来源必须配置为接收相关群消息，接纳策略也必须允许这类候选进入评估。先用 `observe` 查看哪些消息会被判为可接单但不执行，经维护者检查后再决定是否启用 `auto`。只接收 @ 的群不会因为写了一条主动规则，就自动获得所有普通消息。

随后一次可能的工作过程是：

1. **同事正常反馈。** 在已接入的群中说明零记录导出报错，并附可公开的最小样例，无需专门重新整理一份派单提示。
2. **Superagent 判断是否符合规则。** 核对是否属于指定仓库、是否有足够证据、是否是已约定正确行为的小问题；不是把聊天内容当作扩大权限的命令。
3. **符合条件才推进。** 在授权范围内尝试复现、定位并修复。若发现需要决定新的导出语义或协调多个独立模块，就不继续按“小缺陷”自主扩张。
4. **拿到有用结果再交付。** 例如给出修复 PR、复现与验证证据，回到反馈话题，让维护者审阅。不要把不断刷出的调查进度当作收益。

对照另一条反馈：“这个页面看起来不够高级。”没有既定设计方向，不能仅因改动可能只有几行 CSS 就自动选择新样式。它不属于上述明确缺陷规则，不自动改动，也不为每条普通讨论发起追问。

## Superagent 负责什么，人负责什么

- Superagent：从可接收的消息中评估候选，按已授权规则处理明确问题，避免把一般讨论变成任务；交付可用成果而非制造通知。
- 维护者：决定接收哪些消息、谁能授权、哪些规则生效，审查误接单和遗漏，控制资源、权限与合并要求。
- 团队成员：反馈事实和必要线索，不需要因 agent 存在就把所有聊天写成工单。

任务开始后，机器人、CI 或引用文本提供的是上下文，不会替团队授予新的权限。聊天接入也不是隐私授权：私有数据和群消息不能直接发布到公开 PR。

## 与继续使用 Codex 的分工

明确知道要解决什么、正在亲自推动的问题，依然可以直接交给 Codex。Superagent 适合补足“还没有人正式派单”的入口和后续跟进：从日常反馈中识别约定范围内的工作，跨话题和 PR 维护联系。

**值得观察的收益：** 人是否少做了发现消息、整理需求和转述的工作；误判是否产生多余 PR；无价值通知是否打扰团队；遗漏和维护成本能否接受。只有在这些方面表现可靠，主动接单才有价值，不能以“开了多少任务”证明收益。

## 能力依据与边界

基于上游提交 `6337fc823ce20251c8de8085948165c81aaa701e` 的[授权文档](https://github.com/dai-junjie/dsh-superagent-prototype/blob/6337fc823ce20251c8de8085948165c81aaa701e/docs/002-authorization.md)：来源接收、admission、主动规则和 accept mode 共同决定是否进入主动处理。`observe` 记录推断候选的评估但不执行，`auto` 才会接纳匹配规则的主动工作；明确请求另有路径，不能把 `observe` 理解为关闭全部接单。

这不是一套默认生效的规则，也不证明任意反馈都能被理解。部署版本和团队配置需要核对，实际误判、漏判与收益仍需真实使用验证。
