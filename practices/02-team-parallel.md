# 案例二：多人共用 Agent，独立任务并行推进

> 场景化使用案例，不是实测复盘。人物和对话为虚构示例，不代表已测得吞吐、时延或人力节省。

## 团队遇到什么问题

同一个小组里，甲要排查错误，乙要补测试，丙要更新文档。如果所有请求都放进一个长会话，需要有人不断切换上下文；如果每个人各开一个 agent，又容易由个人承担追问、跟进和整理结果的工作。

共享 Superagent 的意义不是把这些内容塞进一个“全知会话”，而是从团队入口拆成各自有范围、有执行上下文的任务。

## 实际怎么用

三个人在已接入的群里分别开启话题并 @ Superagent，目标是互不依赖的模块：

- **甲：排查导入失败。** “这个无敏感数据的样例导入时报错，请定位原因并给出修复 PR。”
- **乙：补日期解析测试。** “按已有日期约定补上月底边界的测试，不改接口；如果发现行为有歧义先指出。”
- **丙：补部署文档。** “按仓库现有配置说明日志目录在哪里，在部署文档中补上入口，不改运行配置。”

甲的任务查到两个可能的业务规则，需要维护者确认，于是在甲的话题中问一个具体问题。此时甲的任务等待回答，乙、丙的独立任务可以在资源允许时继续，而不是整个团队都等甲回复。

乙的测试 PR 和丙的文档 PR 分别回到各自的话题；维护者回答甲之后，甲的任务再继续。每个人主要关心自己的结果，不需要指定某个人逐个找到编码会话、转述反馈、整理进度。

这里展示的是不同任务的生命周期可以独立推进，不承诺三条请求会同时启动，也不保证没有排队。

## Superagent 负责什么，人负责什么

- Superagent：为不同请求维护任务和执行上下文，把必要问题交给相关的人，将各自结果送回来源。
- 提需求的人：说明目标、约束和可用证据，回答真正需要人的问题。
- 维护者：配置可接单的成员和来源，控制并发、机器资源、仓库权限与合并要求。

共享 agent 不等于每个群成员自动拥有权限，也不等于不同人的数据自动隔离。任务目录和身份配置不是操作系统安全沙箱，敏感信息仍要按团队权限管理。

## 与继续使用 Codex 的分工

个人在 Codex 中深入处理一个复杂问题，仍可以是团队的主力工作方式。高频结对、需要人连续做判断的任务，没有必要为了“共享”而迁移。

Superagent 更适合目标明确、能异步交付的团队请求：多人从既有入口提交，任务各自等待或推进。它减少的是人维护和追踪协作会话的负担，不是消除维护者，也不是声称 Codex 不能并行运行任务。

**值得观察的收益：** 一个任务等人时其他任务是否仍有进展；各人的反馈是否回到正确话题；是否还需要专人反复询问和转述。真实吞吐取决于并发配置、机器和模型服务，不能从“支持多个任务”直接推导效率提升。

## 什么时候不适合这样用

- 三个人改同一个接口、同一文件，或彼此依赖的任务：先协调边界与顺序，不把它们当独立任务并发派发。
- 必须马上响应的线上事故：团队的值班和应急机制仍是主线，不能把 agent 的排队当作响应保障。
- 没有足够权限或资源隔离的共享环境：先解决治理问题，不以共享账号替代授权设计。
