# 实践一：从一条消息到可审阅的文档 PR

> 必做 · 实践方案，尚未执行。下文的请求是演示输入，预期不是实测结果。

## 目标

给 agent 一个范围明确的小文档修改，观察消息、任务、代码变更和人工审阅如何关联。终点是人能审阅的 PR，不是机器人回复“完成”，也不要求自动合并。

## 环境与前置条件

- 按上游 [SETUP](https://github.com/dai-junjie/dsh-superagent-prototype/blob/6337fc823ce20251c8de8085948165c81aaa701e/SETUP.md) 准备独立测试部署；已部署者先核对实际版本与配置，不重复初始化。
- 使用自己有权限的测试仓库和飞书测试群；仓库有默认分支、README 和 `docs/` 目录，agent 能推分支、创建 PR。
- 配置该群为消息来源，实验者在允许名单中，使用真实的 @ 提及选中机器人；不要只粘贴显示名。
- 由人审阅、合并；实验不修改生产配置、授权名单或自动合并设置。没有飞书时可在测试仓库的新 Issue 中 @ agent，记录这是 GitHub 变体。
- 开始前记录：项目提交、DSH 版本、操作系统、相关工具版本、测试仓库、来源接收方式、Policy 版本和实验时区。不要复制凭据或完整环境变量。

## 操作步骤

1. 确认测试仓库中 `docs/practice-note.md` 尚不存在，并记录默认分支提交。若已存在，使用新测试仓库，避免覆盖旧记录。
2. 在**新话题**中 @ 机器人，发送以下演示请求；替换目标仓库为本次已配置的测试仓库：

   > 请在测试仓库的 docs/practice-note.md 中新增一篇“实践记录”，写明目标是验证从消息到可审阅 PR 的链路，并在 README 中增加它的相对链接。只改这两个文件，检查链接后提交 PR，由我审阅，不要合并。

3. 记录发送时间，在 Superagent 面板找到对应 Trigger；记录 Decision、Ticket 及关联关系。没有进入系统时先排查来源接收，不能把未收到消息称为拒绝执行。
4. 观察任务是否产出分支、提交和 PR，以及结果是否回到原话题。只查看本次任务，不以内部日志持续刷新代替人实际收到结果。
5. 打开 PR：核对仅改指定文件、内容符合要求、README 相对链接能打开、无敏感内容。记录 PR 头提交和检查结果；若没有 CI，写“未配置 CI”，不能写“CI 通过”。
6. 人工记录审阅结论。若需要修改，在该 PR 的审阅线程提出一个具体问题，观察更新是否仍关联原任务；若无需修改，不为凑步骤制造反馈。是否合并由人决定。

## 预期与成功判据

| 观察点 | 预期 | 如何验证 |
| --- | --- | --- |
| 接单 | 明确请求进入任务处理 | Trigger、Decision 与 Ticket 能对应 |
| 交付 | 存在可审阅 PR，而不只是聊天承诺 | 对照 PR diff、链接和头提交 |
| 范围 | 仅新增记录并更新导航 | 文件列表只有指定两个文件 |
| 人工介入 | 人可以决定修改或合并 | 记录审阅结论；未获授权不自动合并 |
| 返回原处 | 原话题收到可用结果入口 | 核对消息中的 PR 与本任务一致 |

上游将 `ready` 报告关联的开放 PR 表示为等待审阅；它不等于已经合并。正常回复时延受部署、排队和服务影响，本练习不承诺固定分钟数。

## 踩坑与排查

以下是排查提示，不是已经遇到的问题：

- 没有 Trigger：检查群是否配置、机器人是否收到真实提及，以及来源是否健康。
- 有任务但无 PR：看任务是否在等待人工信息、遇到仓库权限问题或检查失败，不能把确认接单当完成。
- PR 存在但原话题没有结果：分别记录交付产物和通知状态，排查消息通道，不重复创建 PR。
- 文档链接错误：以文件所在目录为起点核对相对路径，不能只检查显示文字。

## 清理与后续

审阅后由人决定合并或关闭测试 PR；确认不再需要再清理测试分支。保留脱敏的结果记录。分享时可以用“请求 → 接单 → 修改 → 验证 → 人审”讲解一次实际执行，但不能仅凭此例宣称所有任务都能自主完成。
