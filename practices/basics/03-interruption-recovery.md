# 实践三：隔离环境中的中断与恢复

> 选做 · 实践方案，尚未执行。没有独立部署和可恢复的测试状态就跳过，不在共享服务上演示中断。

## 目标

观察工作中的任务遇到一次受控宿主重启后，是否保留已有成果、继续处理，并避免重复创建 PR。只研究一次明确的恢复路径，不宣称验证了断电、网络故障或所有工具副作用的幂等性。

## 环境与前置条件

- 已完成[实践一](01-message-to-pr.md)，能够识别 Ticket、执行会话、任务目录、分支和 PR。
- 使用独立 DSH profile、状态目录、测试仓库及测试消息来源，不与线上部署共享进程、端口或状态目录；没有其他人的任务运行。
- 维护者事先按实际部署版本的[部署文档](https://github.com/dai-junjie/dsh-superagent-prototype/blob/6337fc823ce20251c8de8085948165c81aaa701e/docs/006-deployment.md)核对正常停止、启动和状态检查的方法，并记录操作。本文不提供可能误停线上服务的通用 kill 命令。
- 预先验证能备份和恢复测试状态，避免复制不一致的运行中数据库；备份、日志和凭据只存放在受控位置，不上传本仓库。备份恢复方法不明确就不执行。
- 记录项目提交、DSH 与工具版本、操作系统、时区、隔离方式和实验前基线提交。

## 操作步骤

1. 先确认测试仓库默认分支中 `docs/recovery-note.md` 尚不存在，README 尚无对应链接，并记录基线提交；若已有同名内容，换用新的测试仓库。然后在新测试话题中 @ 机器人，发送以下演示请求，记录 Trigger 和 Ticket：

   > 请在测试仓库的 docs/recovery-note.md 中新增一篇“恢复实验记录”，写明目标是观察受控重启后的任务恢复，并在 README 中增加它的相对链接。只改这两个文件，检查链接后提交 PR，由我审阅，不要合并。

2. 维护者观察任务进入工作状态，在一次正常、可确认的操作边界记录当前分支、提交、文件状态、PR 是否已存在及头提交。不要通过延长命令、制造错误或加入无意义任务强行拖慢执行。
3. 若任务已经 ready、阻塞或等待人工答复，取消本轮中断并标记“未覆盖工作中恢复”；这些状态与正在运行的 Assignment 不同。
4. 确认只影响测试部署后，由维护者执行预先核对的宿主停止/启动流程。记录停止、启动和服务恢复时间，不修改 Policy、不清空状态、不发送重复请求。
5. 观察原 Ticket 的新 Assignment、恢复说明和后续结果；核对是否沿用任务目录、分支、已有提交与 PR。恢复失败时记录错误和人工介入，停止继续注入故障，使用已确认的恢复办法。
6. PR 可审阅后，由人核对目标内容、链接和变更范围，并对照重启前后仓库记录与原话题交付。特别检查是否重复开 PR、重复提交同一内容或重复发送结果。

## 预期与成功判据

上游公开文档描述：运行中的 Assignment 在宿主重启后会获得恢复说明；执行者应先核对本地目录、git 历史和 GitHub，再重复外部操作。等待、ready、blocked 或 failed 的任务不是同一个恢复场景，除非其后有新的输入。

本轮成功需要：

- 确实覆盖工作中的一次受控重启，并能关联重启前后的同一 Ticket。
- 已有工作没有被错误覆盖，最终 PR 内容符合原请求。
- 对本轮实际发生的外部动作，没有发现重复 PR 或重复交付；若中断前尚未创建 PR，不能据此声称测试过“已有 PR 的复用”。
- 明确记录是否需要人工重试以及恢复耗时，不能把人工修复后的成功写成自动恢复。

这不是逐条数据库一致性测试，也不是“恰好一次执行”的证明。源码设计、文档承诺与本次观察分别陈述。

## 踩坑与排查

以下是排查提示，不是已发生的结果：

- 找不到中断窗口：如实标记未覆盖，不把已完成任务重启后仍存在视为恢复成功。
- 启动了另一套 profile：检查测试进程是否读取原状态目录，不能把空环境中的重新执行算作恢复。
- 重启后无自动进展：核对中断前是否已处于等待/失败状态、来源健康和配置是否变化；记录所需人工动作。
- 不要把“暂停处理”当作中断执行：公开文档说明暂停处理不会打断正在运行的执行者回合。

## 清理与后续

确认测试部署恢复正常；由人关闭或合并测试 PR，再按测试资源保留约定清理。备份和日志保存在受控位置，到期按约定销毁。分享时明确中断发生在哪一阶段，避免把一个小样本推广为任意故障可恢复。
