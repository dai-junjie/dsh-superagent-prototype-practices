## 1. Inline / Spill：长消息如何进入上下文

### 目标与概念

- **Inline**：将近期可能需要的信息直接放入当前模型输入，包括正文片段和相关元数据，减少工具往返。
- **Spill**：将未内联的完整信息保留在当前输入之外，提供可读取的引用；需要时再读回。不是删除剩余内容，也不一定是生成摘要。
- **成功判据**：初始输入没有携带全文，但保留片段与可用引用；沿引用读取后能到达原文末尾。

这是事件注入和工具返回的组织方式，不要求先把模型总上下文窗口塞满。长消息可以覆盖单个对象的长度限制，但不能单独验证累计上下文预算或所有对象类型。

### 复现方法

前置条件：能查看模型初始输入与工具调用的会话记录，并有测试消息的读取权限。仅看飞书聊天气泡无法判断全文是否已注入，无需修改权限或部署配置。

1. 在允许测试的聊天中，明确请求读取一条长消息的末尾信息。
2. 使用自行生成的无敏感内容文本，开头与末尾放不同随机标记，例如 `HEAD_<随机值>`、`TAIL_<另一随机值>`。不要依赖模型可能知道的公开文章判断是否真的读取。
3. 查看发给 Worker 的初始输入，记录是否只有前缀、原文长度和续读入口。若全文已内联，这次未覆盖 Spill；可增大合成文本重试，不要据此认定功能失效。
4. 沿输入的 `read` 引用调用 `orchestrator_read`，从 `offset=0` 开始，严格使用返回的 `next_offset` 续读，直到 `null`。不要猜下一页位置或把其他接口的消息 ID 当作资源引用。
5. 对照源文本核对两端标记及页边界。确认尾部确实经工具进入上下文，排除全文已注入或凭已有知识答对。
6. 保留脱敏证据：初始输入形态、资源类型、分页偏移、总长度、结束标志和标记核对结果。不发布私人对话、真实会话 ID、令牌或本地绝对路径。

下面仅为接口形态示意，**不是本次原始输入或新增执行结果**；引用应使用自己实际收到的值：

```text
初始输入：
  text: "HEAD_<随机值> ...（仅前缀）"
  chars: <原文长度>
  read: "trigger/<测试事件 ID>"

第一次读取：
  orchestrator_read(resource=<read 的值>, offset=0, limit=8000)
后续读取：
  offset = 上一页的 next_offset
  结束条件 = next_offset 为 null
```

### 为什么平时聊天不好验证

- **答对不等于读取**：答案可能来自已有知识或先前上下文。随机尾标与工具轨迹能提供更强证据。
- **读回不等于自动加载**：Spill 保留入口，仍需要按需调用工具，不保证每次读完所有长消息。
- **分页不等于链式召回**：同一对象的 `next_offset` 是续页；链式召回须沿对象间引用走到下一跳。
- **界面折叠不等于 Spill**：须检查模型输入，不能把聊天 UI 的“展开全文”当作注入被截断。
